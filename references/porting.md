# 移植工作流与验证

## 读取边界

普通插件开发只读用户提供的目标游戏本体和 Wiki 插件文档。只有用户明确要求从某个来源移植时，才读取来源内容。
先在用户本体路径的 `kr1/`、`all/`、`all-desktop/` 和 `plugin/` 中找同类实现，再打开来源中的对应文件。
不要对大型来源仓库做全树扫描，也不要把来源项目的架构、全局变量或脚本风格直接带入插件。

## 移植顺序

1. 确认目标 entry、插件类型、来源对象和许可范围。
2. 在目标游戏中定位对应模板、脚本、注册表、动画、声音和资源加载点。
3. 先建立目标插件目录和元数据，再逐项迁移声明、模板、逻辑、资源和文案。
4. 所有模板、声音、图集和语言键加 entry 前缀。与本体冲突时选择明确的新名字，并记录映射。
5. 能通过 registry、模块声明或资源表完成的部分不加 hook。
6. 对每个外部依赖做目标 API 适配，不复制来源的 metatable、`_G` 写入、硬编码枚举和生命周期假设。

## 验证阶梯

- L0：用目标环境的 Lua/LuaJIT 对新增 `.lua` 做语法检查。
- L1：运行本仓库工具的 `validate` 和 `asset-check`，检查 entry、配置字段、资源引用和禁止写法。
- L2：在目标游戏中加载本体模板、动画、声音、语言和图集，确认注册时机正确。
- L3：进入实际地图，验证选择、建造、升级、技能、实体插入/移除、波次和 UI。热重载只在有完整回滚
  证明时测试，未实现可选接口则按重启路径验证。

缺图、缺声和缺动画可能不会让自动测试立刻失败，因此必须查看日志中的资源错误，并结合实机画面确认。

## 目标内参考顺序

先看目标游戏当前的 registry、模板、菜单、资源加载器和同类型本体内容，再看本仓库的
`references/*.md`。本仓库已经总结了所需的目录和字段，插件实现不需要用户机器上存在任何示例插件目录。
